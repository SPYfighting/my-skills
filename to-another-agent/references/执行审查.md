# 审查当前项目

用于用户要求当前 agent 审查项目，或交给当前 agent 一份有效的 `review-request`。审查实际文件和可复跑证据，不依赖聊天摘要；除审查结果外，不修改被审产物、项目 task、handoff 或结果记录。

有请求文件时先验证其协议、范围和锚点。没有请求文件时，以当前用户命令作为审查范围，不为形式完整而制造一份请求文件。

## 审查步骤

1. 读取项目级指令、用户要求、实际产物和必要验证记录。
2. 对照范围检查缺失、越界、错误和证据不足；优先核对后果最大的主张。
3. 每条发现写窄锚点、实际证据和建议动作。
4. 结果写入 `cross-agent-review-files/<YYYY-MM-DD>-<任务简称>-r<轮次>-审查.md`。
5. 给出运行时中立的简短处理提示词。

发现分为：

- **阻断**：不修正则交付不成立。
- **重要**：交付可用但存在实质风险。
- **可选**：质量改进，最多五条。

结论固定为：阻断存在时“需返工”；没有阻断但有重要发现时“有条件通过”；其余为“通过”。

## 结果模板

````markdown
# 审查结果：<任务简称> r<轮次>

- 协议：to-another-agent/v2
- 交接类型：review-result
- 日期：<YYYY-MM-DD>
- 对应请求：`<请求文件>` / 当前用户指令
- 结论：**通过 / 有条件通过 / 需返工**
- 一句话：<最重要结论>

## 1. 核对轨迹

- `<path:line>` —— <核对内容>
- `<只读命令>` → <结果>

## 2. 发现

### F1 `阻断·已核实` <标题>

- 位置：`path/to/file:12-20`
- 问题：<问题>
- 证据：<实际内容>
- 建议动作：<如何处理>

没有发现时写“未发现阻断、重要或可选问题”。

## 3. 对“最不确定处”的逐条回应

<有请求时逐条回应；直接审查且用户未列不确定处时写“无”。>

## 4. 盲区扫描

- <检查范围和结果>

## 5. 上一轮未闭合发现

<首轮写“无”；后续轮次逐条写状态。>

## 6. 未能核实的

- <对象和原因> / 无

- <不进入正式发现的观察> / 无

## 8. 下一位 agent 接手

```text
请读取 `cross-agent-review-files/<本文件名>`，核对发现是否仍适用于当前版本，并把未闭合的阻断和重要问题落实到项目现有任务文件后处理。完成、实质受阻或用户明确要求复审时，使用 `to-another-agent` 技能更新项目记录并生成下一份提示词。
```
````

审查通过时把提示词中的处理动作替换为“更新项目完成状态或保留恢复入口”。除非用户明确要求，不自动创建复审或验收流程。
