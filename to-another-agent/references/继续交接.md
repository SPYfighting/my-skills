# 继续交接

适用于用户只要求换 agent、整理现场或继续工作，没有明确指定专门角色或额外限制的情况。目标是让下一位 agent 用最小必要核验确认可以安全继续，然后从项目自己的入口推进任务。

当前 agent 的默认完成边界是简单整理现场：核对当前状态，更新已有 task、handoff 和必要结果记录，生成接续提示词；不在交接过程中新增独立审查、重做规划或替下一位完成后续任务。

## 整理现场

1. 找到项目根目录、项目级指令和现有 handoff、task/todo、plan、result/report、验证记录。
2. 从文件、版本控制状态、实际产物、验证命令和可观察的远程状态重建事实。
3. 更新相应事实源：
   - 结果和验证写回既有结果记录；只有有证据的事项标为完成。
   - 未完成工作写进既有 task/plan，附输入、输出、具体动作和完成判据。
   - 只有会影响安全继续的不确定现场才写成“接手先验收”任务，附现场、疑点、最小验收动作和通过条件。
   - handoff 只汇总当前现场并指向上述记录。
4. 用户未明确指定角色时固定写 `下一角色：接续方`、`角色来源：default`；不因风险、完成状态或任务规模改成审查方、验收方或其他专门角色。
5. 没有合适载体时才使用下方默认结构。不为普通交接新建专属目录；`cross-agent-review-files/` 只保存独立审查证据。
6. 重读改动，核对路径、状态、命令、时间、下一角色、远程任务和完成判据；存在任务文件时用 `check_relay.py <handoff> --workspace <根目录> --tasks <任务文件>` 核对两者关系。

## 默认 `AGENT_HANDOFF.md`

```markdown
# 项目交接

- 协议：to-another-agent/v2
- 交接类型：continue
- 更新时间：YYYY-MM-DD HH:MM +时区
- 当前角色：负责者 / 规划者
- 当前目标：一句话说明本次交接所服务的目标
- 状态基线：分支、提交或其他可复现版本；非版本库写“无版本控制”
- 后续任务：`tasks/next-agent.md` / 无
- 下一角色：接续方
- 角色来源：default

## 项目现场

当前阶段、关键入口、工作目录和能直接继续工作的最小背景。

## 已完成与证据

- 事项；证据为 `path/to/file:line`、产物路径或可复跑命令。

## 进行中工作

- 当前停点、已产生的中间产物、下一安全动作；没有则写“无”。

## 结果与验证

- 实际运行的命令、时间、结果和未覆盖范围。引用既有结果记录，不复制整份内容。

## 远程任务

无活动远程任务。

## 决策、边界与风险

- 已确定的选择及理由。
- 用户授权或项目范围边界。
- 推断、未核实信息和可能影响后续结论的风险。

## 接手入口

1. 核对状态基线、工作区改动、关键输入和首个待办。
2. 只验收会影响安全继续的“接手先验收”事项。
3. 达到可安全继续的边界后，从最高优先级未完成任务推进。

## 下一位 agent 接手

> 请加载并使用 `to-another-agent` 技能，以接续方身份接手当前项目。先读取 `AGENT_HANDOFF.md` 和 `tasks/next-agent.md`，核对状态基线、当前改动、关键输入和首个待办；确认可以安全继续后，从最高优先级未完成任务推进。完成或实质受阻时，再次使用 `to-another-agent` 技能更新记录并回报。
```

只有用户明确指定专门角色时才替换角色并把 `角色来源` 改为 `explicit`。按实际现场删去不存在的任务文件、截止时间或远程任务分句。

## 默认 `tasks/next-agent.md`

```markdown
# 下一位 agent 任务

- 协议：to-another-agent/v2
- 交接类型：continue
- 下一角色：接续方
- 角色来源：default

## 接手先验收

- [ ] T1 核验具体结论或现场
  - 现场：文件、结果、日志或远程任务位置
  - 疑点：为何当前不能确认
  - 验收动作：下一位 agent 应实际检查什么
  - 完成判据：什么证据足以确认、否定或升级处理

## 待执行

- [ ] T2 完成具体工作
  - 输入：所需文件、数据或前置条件
  - 输出：明确产物
  - 完成判据：可观察的通过条件

## 受阻

- [ ] T3 等待外部条件或用户决定
  - 阻塞条件：当前缺少什么
  - 解锁条件：出现什么状态后可以继续
  - 完成判据：阻塞被解除并更新到“待执行”或完成
```

任务编号只需在当前文件内唯一；项目已有任务标识时沿用原标识。

工作已完成时可不保留任务文件，但 handoff 仍提供中性恢复入口：

> 请加载并使用 `to-another-agent` 技能，以接续方身份读取 `AGENT_HANDOFF.md`，核对当前状态、已有证据和未验证边界；若没有剩余工作，保留现状并等待新任务，若发现未完成事项则继续推进。状态改变或实质受阻时，再次使用 `to-another-agent` 技能更新记录并回报。

## 设计依据

本流程只借鉴公开项目的工作原则，不复制其模板：

- [AgentWorkforce `Peer Review Handoff`](https://github.com/AgentWorkforce/skills/blob/main/skills/writing-agent-relay-workflows/SKILL.md)（Apache-2.0）：协调消息指向实际文件，reviewer 自行读取产物。
- [Entire `review` / `address-findings`](https://github.com/entireio/skills)（MIT）：审查与修复是连续但职责分离的阶段。
- [mirzaakhena `handoff`](https://github.com/mirzaakhena/handoff/blob/main/skills/handoff/SKILL.md)（MIT）：项目状态和审查记录分开，避免两个检查者反复改写同一文件。
- [KitsuneKode `session-handoff`](https://github.com/KitsuneKode/agent-skills/tree/main/skills/session-handoff)、[xiaomaimuchanyiyiba `agent-handoff`](https://github.com/xiaomaimuchanyiyiba/agent-handoff) 和 [WeirdSky924 `agent-handoff-skill`](https://github.com/WeirdSky924/agent-handoff-skill)：交接压缩事实、保留决策与可执行下一步。
