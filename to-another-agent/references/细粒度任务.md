# 细粒度任务

仅在用户明确要求细粒度、逐步执行或需要低歧义执行说明时使用。目标是冻结路线、减少重新设计，并让不同能力与实现方式的接手 agent 都能在每个可修复验证门后继续推进，而不是把“通过条件”当作停止点。

## 编写规则

1. 在现有 task 文件加入以下元数据；没有 task 文件时使用 `tasks/next-agent.md`：

```markdown
- 任务粒度：fine
- 执行策略：persistent
- 下一角色：接续方
- 角色来源：default
```

用户明确指定专门角色时替换 `下一角色` 并写 `角色来源：explicit`。用户明确给出时限时，才按 `references/时限与收尾.md` 增加时间字段。

2. 顶层任务保留复选框，写清目标、输入、输出、总完成判据、默认回退和回报节点。把关键路线、工具、参数和允许的默认回退冻结下来；不要让接手 agent 再次选择实质路线。
3. 步骤按依赖顺序排列。每一步只做一个可观察动作，并带核验、通过条件、未通过动作和证据槽；存在时限时再写预计耗时。
4. 通过后立即进入下一未完成步骤。可修复失败先修复并重验；只有权限不足、安全风险、缺少用户实质决策、不可恢复环境故障或进入收尾时间才暂停交接。
5. 完成步骤时勾选复选框并把“待执行”替换为实际输出、命令结果或窄锚点。只有所有步骤完成且总完成判据满足时才勾选顶层任务。

## 任务模板

```markdown
- [ ] T1 <具体任务>
  - 目标：<单一结果>
  - 输入：<文件、数据和前置条件>
  - 输出：<明确产物>
  - 完成判据：<全部步骤通过后可客观判断的终态>
  - 默认回退：<首选路线失败时仍在授权内的既定方案>
  - 回报节点：S2, S4
  - 执行步骤：
    1. [ ] S1 <单一可观察动作>
       - 操作：<精确路径、命令、参数或编辑对象>
       - 核验：<实际检查或命令>
       - 通过条件：<客观结果>
       - 未通过动作：<修复并重验；命中何种终止条件才交接>
       - 证据：待执行
```

步骤编号在整个 task 文件内唯一。回报节点只选能改变风险、路线或接手价值的节点，不要每一步都回报。只有用户明确提出时限时，才在各步骤增加 `预计耗时`。

## 里程碑与终态回报

接手 agent 在完成预定义里程碑、全部完成、实质受阻或留下活动远程任务时，再次使用 `to-another-agent` 技能；只有用户明确设置时限时才增加“到达收尾时间”触发。不新建回报文件：更新步骤复选框和证据，在 task 的 `## 执行回报` 追加紧凑记录，并同步既有 handoff 与结果记录。

```markdown
## 执行回报

### R1
- 时间：<带时区的绝对时间>
- 状态：milestone / complete / blocked / deadline-handoff / remote-running
- 完成步骤：S1, S2
- 关键结果：<高信号结果>
- 核验证据：<锚点、产物或命令结果>
- 剩余事项：<下一未完成步骤或无>
- 建议下一角色：接续方；仅在用户明确指定时写其他角色
```

每次回报后保留用户明确指定的角色；没有新的明确角色要求时回到 `接续方`。完成全部工作时生成中性恢复提示词，不自动切换为验收方。

## 设计依据

只吸收公开流程原则，不复制模板：

- [AgentWorkforce relay workflow](https://github.com/AgentWorkforce/skills/blob/main/skills/writing-agent-relay-workflows/SKILL.md)（Apache-2.0）：验证门失败后修复并重验，交接只保留高信号现场。
- [Pendia / Addy Osmani `planning-and-task-breakdown`](https://github.com/Pendia/Agent-Skills)（上游 MIT）：任务具有依赖顺序、明确验收条件和验证步骤。
