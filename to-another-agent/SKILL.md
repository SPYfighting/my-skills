# to-another-agent：交接与审查闭环

交付可核验、可继续的现场。项目事实留在既有 handoff、task、plan 和结果记录中；只有独立审查证据进入 `cross-agent-review-files/`。Agent 由用户切换，本技能不自动创建 agent，也不扩大权限。

## 先选主路由

按顺序判断，命中即停：

1. 用户给出 `*-审查.md`，或明确要求处理审查反馈 → 读 `references/处理审查结果.md`。
2. 用户给出 `*-请求.md`，或明确要求执行已有审查请求 → 读 `references/执行审查.md`。
3. 用户明确要求把产物交给下一位做独立审查 → 读 `references/提交审查.md`。
4. 其余情况一律读 `references/继续交接.md`，不根据风险、任务长度、远程状态或完成程度升级路由。

“明确要求”按肯定意图理解，不要求固定关键词。`审查 / review / 独立复核 / 把关 / 挑错` 表示审查；`按审查意见修改 / 修复发现 / 返工` 表示工作方；`监控 / 盯住 / 等待并接收远程结果` 表示监控方；`只规划 / 拆任务 / 制定方案而不执行` 表示规划方；`只执行 / 实现 / 跑完既定计划` 表示执行方；`只验收最终结果 / 确认是否完成且不修改` 表示验收方。普通的“接手、继续、换 agent、整理现场、先核对再做”不表示专门角色；被否定的表达、举例或历史描述也不触发角色或限制。

用户没有明确角色时，`下一角色：接续方`、`角色来源：default`。接续方只做安全继续所必需的现场核验，然后推进现有任务；不把接手核验扩展为独立审查。用户明确指定角色或给出明确审查文档时，写 `角色来源：explicit`。

## 再叠加可选修饰器

- 只有用户明确要求“细粒度、逐步执行、写到每步核验”等同义要求时，才读 `references/细粒度任务.md`。任务看起来复杂或耗时不构成触发。
- 只有用户明确给出结束时间、截止时间、工作时限或等义要求时，才读 `references/时限与收尾.md`。
- 现场确有仍在运行或等待结果的远程工作时，读 `references/remote-work.md` 记录事实；这本身不改变下一角色。

## 共用协议

- 协议标记为 `to-another-agent/v2`；交接类型使用 `continue`、`review-request`、`review-result` 或 `address-findings`。
- 默认只整理当前现场并更新既有 handoff、task 和必要结果记录；缺少载体时才创建 `AGENT_HANDOFF.md` 与 `tasks/next-agent.md`。
- 接手核验以能够安全继续为完成边界：核对状态基线、当前改动、关键输入和首个待办，不主动扩大成全面审查。
- 区分实际验证、来源事实、用户陈述、假设、推断和未核实项；不把聊天摘要当项目事实源。
- 提示词保持运行时中立：只写项目事实、角色职责、应读文件、第一动作、验收与回报条件。`工作方`、`审查方` 等是职责标签，不表示必须创建子智能体；当前环境的模型名、推理等级、服务档位、并发编排和工具调用参数不进入提示词。模型或平台是项目研究对象时可作为任务对象出现，不把它变成接手者的运行要求。
- 每次交接都在文档和回复中原样给出提示词。提示词点明角色、应读文件、第一动作、完成或回报触发条件、适用截止时间和远程状态；用“加载并使用 `to-another-agent` 技能”指代技能，不假设某个平台的调用语法；到触发条件时要求再次使用该技能更新现场。
- 即使工作已完成，也生成供未来恢复的接续提示词；只有用户明确要求验收时才使用验收方。

## 机械核验

新建或更新默认格式文档后运行：

```text
python <skill-dir>/scripts/check_relay.py <文档> --workspace <项目根目录> [--tasks <任务文件>]
```

校验器自动识别 handoff、task、审查请求和审查结果。历史 v2 普通文档及旧审查文档保持兼容；handoff 或审查结果关联任务文件时传入 `--tasks`。

## 回复用户

简述更新的文件、交接类型、下一角色、首个待验收或待执行事项、远程状态和未验证边界。最后逐字给出文档中的下一位 agent 提示词；不存在的任务文件、截止时间、远程任务或复审要求不写入。
