# cross-agent-review：跨 agent 工作审查

两个角色，一次只做一个。**请求方**把刚完成的工作写成可被独立核验的审查请求；**审查方**回到现场逐条核对，产出审查结果。

审查的对象是**产物**，不是请求方的叙述。整套设计都服务于这一句。

## 先定角色

按顺序判断，命中即停：

1. 用户明说了（"请求审查" / "去审一下这份请求文档"）→ 照用户说的做。
2. 上下文里已有审查请求文档，或用户给了它的路径 → 你是审查方。
3. 用户要求为刚完成的工作找人审 → 你是请求方。

三条都不命中就问用户，不要猜。

## 三种交接场景

| 场景 | 怎么交接 | 落盘 |
|---|---|---|
| 跨 agent（默认） | 写进 `cross-agent-review-files/`，另一个会话或设备上的 agent 读文件 | 两份都写 |
| subagent | 主 agent 把请求内容直接写进 subagent 的 prompt，审查结果回到对话 | 都不落盘，但内容项一条不少 |
| 用户手动转达 | 同跨 agent | 两份都写 |

## 文件与轮次

文档放在项目根目录的 `cross-agent-review-files/`，目录用全称命名以避开与任务自身目录撞名。目录不存在就建。

```
<YYYY-MM-DD>-<任务简称>-r<轮次>-请求.md
<YYYY-MM-DD>-<任务简称>-r<轮次>-审查.md
```

文件名自带全部定位信息，`ls` 一次就能选出该读哪份，因此不另建索引文件——索引是对 `ls` 的复制，只会与实际文件脱节。

- **审查方选文件**：用户给了路径就用它；没给就取任务简称匹配、轮次最大、且尚无同轮次审查文件的那份请求。
- **请求方开新轮**：同一任务再次请求时轮次加一。

**增量**——轮次大于 1 时只处理本轮变更和上一轮未闭合的发现，上一轮已确认通过的部分不重审。把 token 花在已有结论上不产生新信息。

## 两侧共用的硬规则

- **锚点**——每条关于产物的主张都带 `文件路径:行号区间` 或可复跑的命令。**锚点尽量窄**，指到具体行段而不是整个文件：锚点宽度直接决定审查成本，指到整个文件就等于要求审查方读整个文件。
- **原话**——用户需求逐字引用。转述会把请求方的理解混进基准里，"从一开始就理解偏了"这类最要命的偏离就再也查不出来。多轮修改过的需求，把修改也逐条摘出并标明最终生效的版本。
- **只读**——审查方全程只读：读文件、跑只读命令、查外部资料。发现的问题写进审查结果交回请求方去改。用户明确要求审查方动手时才改。
- **证据等级**——每条判断依据标明性质：实际验证过、来源事实、用户陈述、假设、推断。

## 机械核验

```
python scripts/check_review_doc.py <文档路径> --workspace <工作区根>
```

检查文件命名、必需章节是否齐全、锚点是否指向真实存在的行、审查文档的分级标签是否合法、可选级条数是否超上限。两侧落盘后都跑它；审查方开工时先对请求文档跑一遍，锚点对不对由它一次报完。

## 走哪一侧

- 请求方 → `references/请求方-写审查请求.md`
- 审查方 → `references/审查方-执行审查.md`

subagent 场景同样各读一侧：主 agent 按请求方那份组织 prompt 内容，subagent 按审查方那份执行并回话。
