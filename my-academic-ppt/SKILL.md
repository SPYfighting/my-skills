# My Academic PPT

把科研内容做成能讲清楚、能看明白、能核对证据的演示文稿。组织原则是**围绕一个清楚的问题或判断，提供足够的视觉解释与证据，建立明确的阅读层级**。多模块只是其中一种组织方式。默认浅色、克制配色；用户的模板、语言和用途优先。

## 设计自由度

把参考稿当成设计词汇库，结合当前内容选用、混合或新建构图。分栏、虚线框、粗箭头、底部结论、章节页、进展标签和致谢均按用途选择；没有必要就省略。字体、配色、版式和章数不固定。守住证据准确、演示可读与验收真实这三项底线，而不是复制模板。

## 开始工作

先读需求、现有稿和参考材料，确认听众、时长、交付格式、已有证据及本轮范围。能自行查明的先查；把影响结构或结论的缺口集中询问，继续不依赖回答的工作。用户只要求局部调整时，不重做已认可页面。

新稿先列逐页规划：本页问题或主判断、证据来源、图形形式、模块关系、讲述时间。若用户明确要求分阶段交付，按阶段交付；否则规划属于内部制作过程，继续完成 PPT。篇幅由内容和时间决定。

## 设计与制作

1. **组织叙事。** 新稿或重构时读 [叙事与讲稿](references/narrative.md)。根据长度和用途组合目录、章节入口、技术内容、总结及结束页；短报告或局部页面可省略导航与仪式性页面。章节入口用主标题和最简真实路线揭示本章要解决的问题。
2. **选择布局。** 排版前读 [布局与视觉语法](references/layouts.md)，查看 [原创布局图册](assets/layout-gallery.svg) 作为若干示例；指南还覆盖不对称证据、上下两层、逻辑梯级、整体与局部等构图。让方法、证据和结论占据不同层级，避免纯文字卡片堆叠或无解释的大图。信息不足时收束页面，不用装饰图制造内容。
3. **安放证据。** 选图、重绘或写科研结论时读 [图件与证据](references/figures-evidence.md)。研究结果、模型预测、文献示意和研究计划分别表述。图片承担解释任务，资料可追溯；必要的学术限定保留在读者能看到的位置。
4. **生成成品。** 制作或导出时读 [实现与验收](references/build-qa.md)。使用当前环境可用的演示工具，文字、箭头和可维护的图表尽量可编辑。整页截图不能替代可编辑 PPT，除非用户明确接受。
5. **配齐讲稿。** 用户未要求例外时，每页提供可直接讲述的备注，语言跟随汇报语言。备注写口头汇报正文，来源清单和制作说明另存；其余规则见叙事指南。

首次确立风格，先做少量覆盖主要页面类型的代表页，渲染后检查，再扩展整稿。已有认可稿时直接复用其视觉语法，不新增重复确认环节。

## 验收与交付

交付前落实实现指南中的三项独立检查：**科学内容、实际画面、文件结构**。有演示生成库并不代表有渲染器；检测到缺失时只报告实际验证范围。

结构检查命令（路径相对于本技能根目录；`python` 指可用的 Python 3）：

```bash
python scripts/audit_pptx.py /path/to/deck.pptx --require-notes --output /path/to/audit.json
```

检查脚本不判断美观、文字溢出或科研真假。必须另看实际渲染；复核修改页及受影响的相邻页，整体风格首次建立或大规模改版时看全稿。新增图件、数据或换字体后检查其实际导出表现。

交付可编辑 PPT、所需预览及讲稿，保留复现所需源文件和来源索引。校验最终文件与已审阅版本一致。只在用户要求或覆盖前确有恢复需要时保留明确的恢复副本，不积累无意义版本。

## 环境与可移植性

核心规则采用通用 Markdown 和相对路径。Codex 可使用 `agents/openai.yaml` 的可选界面元数据；其他 Agent 直接读本文件。工具选择、缺少能力时的处理见实现指南，不依赖特定插件或本机路径。技能不授权安装、发布或上传研究材料。
